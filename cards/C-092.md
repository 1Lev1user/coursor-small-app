## Goal
Two hardening fixes from the C-087 review (PR #81, reviewer opus) to the new .xls reader, which reads untrusted files on the person's phone:
1. A crafted file of up to 10 MB can no longer make the reader allocate about 160 MB before it gives up with "damaged". On a low-memory phone that much memory could crash the tab.
2. The workbook is read from the file's root storage only. If a bank file ever embedded another Excel object, the embedded workbook would otherwise be read instead of the statement.

## Notes
Code at 658c156 (src/import/xls.js):
- `readMini` (~166-182) allocates `new Uint8Array(needed * 64)` from the directory entry's declared size before it checks that the mini stream is that long. The cutoff is `header.getUint32(56)` (~163). With the cutoff set to 0xFFFFFFFF, a huge declared size and a long mini-FAT chain, the output buffer reaches about 16 times the file size before the per-sector check fails (the reviewer measured a 169 MB peak for a 9.4 MB input).
  Fix:
  - any cutoff other than 4096 → DAMAGED ([MS-CFB] fixes it at 4096);
  - before allocating, refuse with DAMAGED when `entry.size > miniStream.length`;
  - for FAT streams (`readSectors`), refuse when the declared size is larger than the file.
- `find` (~186) returns the first stream entry with the name anywhere in the directory, not only a child of the root storage. Fix: collect the root's direct children by walking the red-black tree from the root entry's child id (offset 76 of the entry; left and right siblings at 68 and 72; NOSTREAM 0xFFFFFFFF), with a visited guard against loops. `find` looks only in that set. This applies to Workbook, Book and EncryptedPackage alike.
  To read the child ids, keep `child`, `left` and `right` on each directory entry where they are parsed (~155).
- Tests (new file; build the CFB in the test as test/importXls.test.js does, without importing from that test file):
  1. cutoff 0xFFFFFFFF with a huge declared Workbook size → DAMAGED, and the call finishes in under 1 s.
  2. a declared size larger than the file → DAMAGED.
  3. an embedded storage holding its own "Workbook" stream that comes before the root's Workbook in directory order → the root's workbook rows are read.
  4. a directory whose sibling ids form a loop → DAMAGED, no hang.
  5. the fixture test/fixtures/xls/citadele-like.xls still reads the same 79 rows.
