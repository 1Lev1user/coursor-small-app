## Goal
Money moved between the person's own accounts (a top-up of Revolut from the main bank, savings moved back) is imported as one expense and one income, so both totals are inflated until every row is fixed by hand (research/3.0/D-bank.md section 12, VERIFIED). After this card, when one import holds a money-out row and a money-in row with the same EUR amount within one day of each other, both are pre-set to Transfer (not counted) in the Categorise step. The person can still change them. A saved rule always wins.

## Notes
- `defaultDecisions` (core.js ~379) today: kind from a matching rule, else expense/income by direction; C-090 adds an MCC category hint.
- Pairing rule:
  - Pair a money-out row with a money-in row of the same `amountCents` and `currency`, whose dates are at most 1 day apart, inside the SAME import.
  - Each row pairs at most once. Choose the nearest date, then the earlier row.
  - Skip rows that already matched a saved rule, rows marked as duplicates (`include` false) and rows whose amountCents is null.
  - Both legs of a pair get kind 'transfer'.
- Do not pair on amount alone across very common small amounts: require amount >= 1000 cents (10.00 EUR), or the same counterparty/description text. Write this threshold as a named constant. Planner: verify it does not pair a coffee refund with a coffee.
- Tests (new file, made-up rows):
  - a 100.00 out on 2026-10-05 and a 100.00 in on 2026-10-05 or 2026-10-06 → both transfer;
  - 2 days apart → not paired;
  - different amounts → not paired;
  - three rows (two outs, one in) → only one pair;
  - a saved expense rule on one leg → that leg keeps the rule and the other is not paired;
  - 4.50 out and 4.50 in with different texts → not paired (threshold);
  - rows without a pair keep exactly today's decisions (deepEqual).
- Revolut Type values (TRANSFER, EXCHANGE, TOPUP) are handled in C-064 together with the Status column, because they need a new optional column.
