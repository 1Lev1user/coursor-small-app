## Goal
A quote character inside an unquoted field (a description like `PIZZA 12" MARGARITA`) no longer opens a quoted section that swallows the following lines. Today 25 of 30 rows vanish and the screen says only "1 line was skipped".

## Acceptance
- `node --test test/importStrayQuote.test.js` exits 0
- `node --test test/importStrayQuote.test.js 2>&1 | grep -E '^# pass ([6-9]|[1-9][0-9])'` exits 0
- `node --test test/importText.test.js` exits 0
- `node --test test/csvQuoting.test.js` exits 0
- `npm test` exits 0

## Do not touch
- existing test files (the quoting tests in importText.test.js:129-141 must stay green: quoted field with delimiter and newline, doubled quotes)
- src/views/import.js, core.js, xlsx.js, xml.js, sw.js

## Notes
Source: D-bank.md problem 5 (VERIFIED, probes p14_quote.mjs, p14b.mjs), independently confirmed in D-bank-verify.md item 4 (probes c4.mjs, c4b.mjs, c4c.mjs). Likelihood for a given bank is UNVERIFIED (depends on whether it quotes embedded quote marks).

Cause: `tokenize` (src/import/text.js:56-118, quote handling :67-87) opens a quoted section at any `"` (:83), not only at the start of a field (RFC 4180), and reads to the next `"`, which never comes.

Fix: a `"` opens a quoted section only when the field so far is empty (allow leading spaces, `field.trim() === ''`). Elsewhere it is an ordinary character. If the end of input is reached while still inside quotes, discard that result and tokenize the text again for that delimiter treating every `"` as an ordinary character (lenient reading), so a truncated or malformed file keeps its line structure. `scoreDelimiter` (:120-147) calls `tokenize` once per candidate delimiter; the retry must keep that cost reasonable (only the unterminated case pays twice).

The fix was prototyped by the planner on a copy of text.js: all 67 tests of importText.test.js pass and the cases below behave as listed (a lenient retry inside `tokenize` that returns `tokenize(text, delimiter, true)` when `inQuotes` is still true at the end).

Regression tests (new file, synthetic, through `parseDelimited`):
1. The failing input from the research: header `Date;Description;Amount` and 30 data rows `2026-03-NN;Shop N;-N,00` (NN = 01..30, N = NN as a number) where row 5 is `2026-03-05;Pizza 12" large;-5,00`. EXPECTED: 31 rows, `rows[5]` equals `['2026-03-05', 'Pizza 12" large', '-5,00']`. ACTUAL before: 6 rows, 4 imported, one "unparsable amount" line.
2. The same file with the stray quote on data row 2 (before: 1 imported), row 15 (before: 14 imported) and row 28 of 30: always 31 rows.
3. The D-bank variant `17.09.2026;PIZZA 12" MARGARITA;-12,50;EUR` as the 5th of 30 rows with delimiter ';': 31 rows, 4 fields each.
4. Comma-delimited variant with quoted amounts (`"-12,50"`) plus one stray quote in a description keeps the amount column readable (before: "Choose the amount column", 0 imported).
5. Controls unchanged: `'Datums;Apraksts;Summa\n13.04.2026;"Coffee; extra note\nsecond line";12,50\n'` still gives 2 rows with the multi-line field; `'a;b\n1;"She said ""hi"""\n'` still unescapes; a field with a leading space before the opening quote (`1; "x;y"`) is read as one field.
6. Unterminated quote at the end (`a;b\n1;"never closed\n2;x\n`): returns 3 rows by the lenient reading instead of 2 rows with a merged tail.
