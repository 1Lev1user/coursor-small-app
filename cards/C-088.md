## Goal
In a Citadele statement every amount sits in one column "Debets/Kredīts" with a sign (-8.8 spent, 1140.41 received). The Columns step guesses it as a Debit column, so every row, the salary included, is imported as money out. After this card the column is guessed as a signed Amount, "Trans. Nr." is the bank reference that duplicate detection uses, and the bank's footer lines (turnover and fee totals) are reported as summary rows instead of "unparsable date".

## Notes
Reproduction on main 4aab875 (planner, 2026-10-17), header and rows in the owner's shape:
`guessColumns(['Datums','Veids','Darījuma detaļas','Maks. Nr.','Trans. Nr.','Debets/Kredīts'], rows)` gives `{date:0, description:2, debit:5, amount:-1, credit:-1, direction:-1, bankRef:-1}`; `rowsToStatement` then turns `16.10.2026 ... 1140.41` into `direction: 'out'`.

Cause 1: `CATEGORY_ORDER` (text.js ~359) tries 'debit' before 'amount' and 'direction'; the normalised header "debets/kredits" contains the debit keyword 'debets' (KEYWORDS.debit ~346), so it becomes the debit column. The swap to a direction column (~469) applies only when the samples are D/K letters.
Fix: a header that holds both a debit word and a credit word (normalised: 'debets/kredits', 'debit/credit', 'debit / credit', 'дебет/кредит', 'd/k' handled as today) is a signed Amount column when its samples are amount-like (`isAmountLikeValue`), and a Direction column when its samples are direction values (`isDirectionValue`, as today). The existing D/K direction keyword cases (KEYWORDS.direction) must stay green.

Cause 2: KEYWORDS.bankRef (~352) has no 'trans. nr.'. Add the bank's own transaction id headers: 'trans. nr', 'trans nr', 'transakcijas nr', 'transakcijas numurs', 'darijuma nr', 'номер транзакции'. "Maks. Nr." (payment order number, repeats and is empty for card rows) stays unmapped. Keep the existing rule in the comment: never a payer reference.

Cause 3: the footer lines "Debeta apgrozījums:", "Kredīta apgrozījums:", "Komisiju summa", "Kopējā izejošo maksājumu summa bez komisijām" have no date and land in skipped as 'unparsable date' (only "Beigu atlikums:" is caught by `isSummaryCell`, ~836). Add 'debeta', 'kredita', 'komisiju', 'kopeja', 'izejoso', 'ienakoso', 'maksajumu', 'bez', 'komisijam' to SUMMARY_QUALIFIERS and 'summa' to SUMMARY_CORE_WORDS only if the whole-cell rule still keeps transactions; a row with a valid date is never a summary row (existing tests in importBalanceRows.test.js guard this).

Cause 4 (small): `inferDateFormat` returns null when every day in the column is 12 or less, so a statement for 1-12 October asks the date question. When the separator is '.' and the column is ambiguous, return 'DMY' (day-first with dots is the only dotted order in the bank formats the research found; MDY with dots was not seen: UNVERIFIED for banks outside LV/EE/LT). Slash and dash ambiguity stays null.

Tests (new file test/importCitadeleColumns.test.js, synthetic rows in the owner's shape, made-up names):
1. `guessColumns` on the Citadele header and 4 rows → amount 5, bankRef 4, date 0, description 2, debit -1, credit -1, direction -1.
2. `rowsToStatement` with that layout: -8.8 → out 880; 1140.41 → in 114041; bankRef 'FT00000000000B'.
3. Footer lines as above → skipped with reason 'summary row'; a row `14.10.2026;PIRKUMS;"... SUMMA KAFE ..."` with a date stays a transaction.
4. 'Debit/Credit' header with D/C letters still becomes the direction column (existing behaviour).
5. `inferDateFormat(['01.10.2026','05.10.2026','12.10.2026'])` → 'DMY'; `inferDateFormat(['01/10/2026','05/10/2026'])` → null.
6. The whole table from the C-087 fixture shape (header at index 3 after the preamble rows): `findHeaderRow` → 3 and, with the guessed layout, money in total equals the sum of positive amounts and money out the sum of negative ones.
