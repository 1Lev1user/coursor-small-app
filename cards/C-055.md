## Goal
Amounts written with the currency after the number ("-12,50 EUR", "12,50 €") are read as 12.50, not as 1250.00. Today the guessed decimal separator is wrong for these files, every amount is 100 times too large and the Columns step shows no warning.

## Notes
Source: research D-bank.md problem 1 (VERIFIED by running the modules), independently confirmed in D-bank-verify.md item 1 (probe c1.mjs). Files are synthetic.

Cause: `guessDecimalSeparator` (text.js:311-324) tests each raw sample cell with `/\d,\d{1,2}\)?-?$/` and `/\d\.\d{1,2}\)?-?$/`. A trailing " EUR" or " €" stops the match, so the fallback '.' wins; `parseAmountWith(value, '.')` then treats ',' as a thousands separator. The same end-anchored pattern is `DECIMAL_TAIL` (src/views/import.js:79), used by `layoutFitsSample` (:82-97). A saved layout with the wrong separator therefore "fits" such a file and the Columns step is skipped (startTable, import.js:579-599). Fix both places together. Since owner decision 21 the Check panel (C-057) is shown on every import, so a total 100 times too large is also visible at the top of the Duplicates step when a remembered layout skipped the Columns step; this card still fixes the cause.

Fix outline: strip the same decoration `parseAmountWith` strips (non-breaking space to space, unicode minus, trailing D/C/K mark, leading or trailing 3-letter currency code or symbol) before testing. Decide by the LAST separator in a cell followed by 1 or 2 digits ("1.234,56" gives ','; "1,234.56" gives '.'); a cell such as "1,234" (3 digits after the separator) decides nothing, go to the next sample. Leading forms ("EUR -12,50", "€12,50") already work and must keep working.

The outline was prototyped by the planner on a copy of text.js (an exported `stripAmountDecoration` used inside `guessDecimalSeparator`): all 67 tests of importText.test.js pass and cases 1-4 and 6 below give the stated results.

Regression tests (new file, all synthetic). Pipeline for each: `parseDelimited` -> `findHeaderRow` -> `guessColumns(header, firstRows)` -> `rowsToStatement(rows, headerRow, { columns: guess.columns, decimalSeparator: guess.decimalSeparator, dateFormat: guess.dateFormat })`.
1. The failing input from the research (semicolon file):
   `Datums;Apraksts;Summa` / `13.09.2026;S0;-12,50 EUR` / `14.09.2026;S1;-3,20 EUR`.
   EXPECTED: decimalSeparator ',', amountCents [1250, 320], direction 'out'. ACTUAL before the fix: decimalSeparator '.', amountCents [125000, 32000].
2. Same shape with `12,50 €` (direction 'in', 1250), with `-12,50<U+00A0>EUR` (1250 out), and with `-1 234,56 EUR` (123456 out; before the fix 12345600).
3. Mixed column `-12,50 EUR` and `-1.234,50 EUR`: decimalSeparator ',', amounts 1250 and 123450, `skipped` empty (before the fix the second row was "unparsable amount").
4. No regression, dot decimals: `-12.50 EUR`, `-3.20 EUR` gives '.', 1250 and 320; leading forms `EUR -12,50` and `€12,50` give ',' and 1250.
5. `layoutFitsSample({ decimalSeparator: '.', dateFormat: 'DMY', columns: { date: 0, amount: 2 } }, [['13.09.2026', 'S0', '-12,50 EUR']])` returns false; the same with decimalSeparator ',' returns true.
6. A cell that decides nothing ("1,234 EUR") does not flip a separator that other samples decided: `13.09.2026;S0;-1,234 EUR` then `14.09.2026;S1;-3,20 EUR` gives ',' (the second sample decides); the first row stays skipped as "unparsable amount" (three decimals are rejected, existing behaviour).
