## Goal
Two gaps from the C-093 review (PR #85). Neither affects the Citadele format; both matter for other banks' CSV and Excel files:
1. A transfer to a payee whose IBAN belongs to a country outside the 30-country table (for example LI, IS, UA, TR, AE) gets an empty counterparty, because the token is no longer recognised as an IBAN.
2. An 11-digit personal code written without a hyphen inside a transfer's purpose lines is kept in the entry text.

- Complete `IBAN_LENGTHS` (src/import/details.js, C-093) from the official SWIFT IBAN registry (ISO 13616). Planner and worker must cite the registry release they used. Values from memory are not accepted: the C-093 planner listed about 24 more countries from memory as UNVERIFIED (IS 26, LI 21, MC 27, SM 27, AD 24, GI 23, UA 29, RS 22, ME 22, MK 19, AL 28, BA 20, XK 20, MD 24, GE 22, TR 26, SA 24, AE 23, QA 29, KW 30, BH 22, IL 23, LB 28, JO 30).
- Scrub `\b\d{11}\b` from the transfer purpose lines only when the line also names a personal code ("personas kods", "p.k.", "персональный код") or when the 11 digits form a valid Latvian personal code. An invoice or customer number must not be scrubbed by accident; the planner decides the exact rule and writes the tests for both sides.
- Source (2026-10-17): the SWIFT registry site is not reachable from the cloud session, but the npm package `ibantools` (reachable via registry.npmjs.org) carries a country specification table generated from the SWIFT IBAN registry. Use its published table (cite the package version and file in a comment); do not add the package as a dependency, copy the lengths only. Countries in ibantools marked as not SEPA/IBAN-registry (partial or experimental) are left out.
