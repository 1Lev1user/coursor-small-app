## Goal
Typing a thousands separator ("1 200,00", "1,200.00", "1.200,00") in an amount field gives the right amount instead of an error, and when an amount is refused the message says what is wrong (empty, zero, negative, or the format) instead of one generic sentence.

`src/money.js` `parseAmount` (:13-37) today does `trimmed.replace(',', '.')` and then `^\d+(\.\d{1,2})?$`. New rule, applied before that regex, only when the whole input matches one of three group patterns (groups of exactly three digits, first group one to three digits):
- space groups (space, no-break space U+00A0 or narrow no-break space U+202F), optional decimal part with `.` or `,` of one or two digits: always unambiguous, accepted. `1 234` is 1234.00.
- comma groups with optional `.` decimals: accepted only when there are at least two groups or a decimal part. `1,234.56` and `1,234,567` are accepted; `1,234` is NOT (it could be 1.234; it stays refused as it is today).
- dot groups with optional `,` decimals: same rule. `1.234,56` and `1.234.567` accepted; `1.234` stays refused.
After removing the group separators the existing regex and cents arithmetic run unchanged.
A scratch implementation with these three patterns was run against the cases below and matched all of them (not committed anywhere):
```js
const space = /^\d{1,3}(?:[   ]\d{3})+(?:[.,]\d{1,2})?$/;
const comma = /^(\d{1,3}(?:,\d{3})+)(\.\d{1,2})?$/;   // accept if m[1].split(',').length > 2 || m[2] !== undefined
const dot   = /^(\d{1,3}(?:\.\d{3})+)(,\d{1,2})?$/;   // accept if m[1].split('.').length > 2 || m[2] !== undefined
```
Accept (cents): `'1 234'` 123400, `'1 234,50'` 123450, `'12 345.6'` 1234560, `'1 234,50'` 123450, `'1,234.56'` 123456, `'1,234,567.89'` 123456789, `'1,234,567'` 123456700, `'1.234,56'` 123456, `'1.234.567'` 123456700, plus the existing `'12.50'`, `'12,50'`, `'1234.5'`.
Reject (null): `'1,234'`, `'1.234'`, `'12.345'`, `'1,2,3'`, `'1.2.3'`, `'1 2'`, `'12 34'`, `'1,23,456'`, `',234'`, `'1,234.567'`, `'1 234 5'`, `'1.234,5,6'`, `'1,234,56'`, `'1234,567'`, `'12€'`, `'1,234.'`, `'-1,234.50'`. `'12.345'`, `'1,2,3'`, `'1.2.3'`, `'1 2'` and `'-5'` also appear in test/money.test.js and must keep passing unchanged.

New `export function amountProblem(input, { allowZero = false } = {})` in money.js returns `''` when `parseAmount(input, { allowZero })` is not null, otherwise exactly one of: `Enter an amount.` (empty or not a string); `Amounts cannot be negative.` (trimmed text starts with `-`); `Enter an amount greater than zero.` (parses as zero and `allowZero` is false); `Use a number like 1234.56 or 1234,56, with at most two decimals.` (everything else).

Use it only in the two forms named in the findings: the Monthly budget form in `src/views/settings/plan.js` (before C-041 the two literals `Enter a valid amount of zero or more.` are at :93 and :102; after the split find them in `savePlan` by that text; budget and, while the field still exists, usual income, `allowZero: true`) and `src/views/settings/goals.js:175` and `:226` (`allowZero: false`). Replace the literal with `amountProblem(value, options)` and keep the surrounding flow. C-045 later adds the zero-budget confirmation to the same form: a budget of 0 still parses (`allowZero: true`) and is confirmed there, not refused here.

Tests, new `test/moneyThousands.test.js`: every accept and reject case above via `parseAmount`; `allowZero` with `'0'` and `'1 000'`; `amountProblem` for `''`, `'-3'`, `'0'` (false and true), `'abc'`, `'12.345'` and a valid value (`''`).
Risk is medium only because `parseAmount` is shared by every amount field; the change must not alter any input that parses today.
