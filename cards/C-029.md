## Notes

Never assume a field exists on an entry created in the same session (the import builds entries without `sourceId`; test/importCore.test.js:246 asserts the exact income keys): treat missing as ''.

model.js (line numbers of today's file):
- :1 `SCHEMA_VERSION = 2` becomes 3. `defaultData()` (:69-142) gains settings `trackingStartMonth: ''`, `incomeSourcesFrom: ''`, `balanceStart: null`, and top-level `incomeSources: []`. `version` stays `SCHEMA_VERSION`.
- Meaning of the new fields (the later cards rely on exactly this):
  - `settings.trackingStartMonth`: 'YYYY-MM' or ''. First month the owner tracks. Set by setup (C-034); for migrated data = earliest month among expense dates, income dates and `monthPlans` keys, '' when none.
  - `settings.incomeSourcesFrom`: 'YYYY-MM' or ''. '' means the old rule (usual income counted from the 1st of every month). A month key means: from that month on, income is real entries only and income sources drive the expectation (C-031). Set when the first income source is created (C-033, C-034).
  - `settings.balanceStart`: null or `{ cents: integer (may be negative), date: 'YYYY-MM-DD' }`. The money on hand at the start of that date (C-038).
  - `incomeSources[]`: `{ id, name, incomeCategoryId, expectedCents (integer >= 0), dayOfMonth (1-31), weekendRule ('keep'|'before'|'after'), active (boolean), startMonth ('YYYY-MM' or ''), skippedMonths (array of 'YYYY-MM') }`.
  - `incomes[].sourceId`: string, '' when the entry is not tied to a source.
  - `subscriptions[].skippedMonths`: array of 'YYYY-MM' the owner skipped (C-035).
- Export `earliestDataMonth(data)` (min month key over `expenses[].date`, `incomes[].date`, `Object.keys(monthPlans)`, '' if none). C-030 and C-032 import it.
- Export `normaliseIncomeSource(raw)`: returns null when `raw` is not an object or has no non-empty string `id`; otherwise a clean object with the fields above (name trimmed and cut to 40 characters; `expectedCents` not an integer >= 0 becomes 0; `dayOfMonth` not an integer 1-31 becomes 1; unknown `weekendRule` becomes 'keep'; `active` not false becomes true; bad `startMonth` becomes ''; `skippedMonths` filtered to valid month keys, de-duplicated).
- `normaliseEntry` (:155-172): when `!isExpense`, `entry.sourceId = stringOr(entry.sourceId)`. Do not touch the expense branch.
- `MIGRATIONS[2]` after `MIGRATIONS[1]` (:178-190), same style: deep copy, `version = 3`, `settings = { ...settings, trackingStartMonth: earliestDataMonth(next), incomeSourcesFrom: '', balanceStart: null }`, `incomeSources = []`, incomes get `sourceId: ''` (keep an existing string), subscriptions get `skippedMonths: []`. No record is dropped or reordered. The step must not read the clock (the migration must be repeatable).
- `normalise` (:219-356): after the existing settings handling (:261-282) repair the new fields the way the neighbours are repaired: `trackingStartMonth` and `incomeSourcesFrom` must match `/^\d{4}-(0[1-9]|1[0-2])$/` else ''; `balanceStart` must be an object with an integer `cents` and a date that passes `monthKeyOf`-style validation (import `monthKeyOf` from months.js) else null; `incomeSources` not an array becomes []; map through `normaliseIncomeSource` and drop nulls; each subscription gets `skippedMonths` repaired the same way (accept subscriptions without the field, test/subscriptions.test.js builds them without it).
