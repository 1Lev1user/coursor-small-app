## Notes
Owner decision 12 (research/3.0/decisions-3.0.md): plan changes (budget, salary) apply from the current month on; past months keep their plan. Income sources (C-030) need no freezing: a payday is read from the entries, and an edited expected amount only matters from now on.

Cause (observed in the app on a fresh profile, and by reading the code): a month with no frozen snapshot is computed from the live settings (`getMonthPlan`, budget.js:174-180 returns `buildPlanSnapshot(data)` of today's settings). A snapshot is only created when the first entry lands in that month (add.js:594, 1493, 957, month.js:394, 482, goals.js:217, import/core.js:637, app.js:177). So months without entries, and every month of data that came from an old backup or an older version that never froze them, change when Settings > Plan is saved (plan.js:108-112) or a category share changes (categories.js:69, 99, 230; shared.js:356, 369, 446). The owner saw September change from budget 1,000 and income 2,000 to 600 and 500. Line numbers are from `main-work` at 6788db8; verify before editing.

Add to budget.js:
```
export function freezeElapsedMonths(data, now = new Date())
```
It walks every month key from `firstTrackedMonth(data, now)` (src/incomeSources.js, C-030) up to and including the month before `currentMonthKey(now)`, calls `freezeMonthPlan(data, monthKey)` for each month that has no entry in `data.monthPlans` AND has at least one expense or income dated in it (amended 2026-10-04 after the C-032 review: freezing empty months changed the Chart history and year totals and removed the import's plan choice for them; an empty past month keeps today's behaviour), and returns how many snapshots it created (0 when nothing to do). It never touches the current or a future month and never creates a snapshot for a month before the first tracked month. It freezes with the settings as they are at that moment, which is exactly what the month was displaying, so no number on screen changes the first time it runs; this includes the old usual income of months that still count the old way. Import `firstTrackedMonth` from './incomeSources.js'; budget.js must not create an import cycle (incomeSources.js imports only months.js and model.js).

Hook in app.js `render()` (app.js:467-516): after the `setupComplete` early return (:473-489) and before `view.render` (:507), add `if (freezeElapsedMonths(app.data) > 0) { saveToStorage(app.data); }` (use the same storage function `save()` uses at app.js:87; do not call `save()` itself, it calls `render()` again). Ignore a failed write: the freeze is repeated on the next start. A render after midnight on the 1st therefore freezes last month before any later form submit can change the live settings.

Known gap, not covered here: the freeze runs on render, so a form submitted in the same instant the month turns over, without any render in between, can still rewrite the month that just ended. State it in a code comment.

test/pastMonthsFrozen.test.js (new, fixed `now` = `new Date(2026, 9, 4)`) must assert:
1. Data with expenses in Aug and Sep 2026 (no snapshots), `settings.monthlyBudgetCents` 100000: after `freezeElapsedMonths`, `monthPlans` has '2026-08' and '2026-09' and not '2026-10'; returns 2. A second data set with expenses in May and Sep only: May and Sep are frozen, June to August are not (returns 2).
2. Set `monthlyBudgetCents` to 60000 and `usualMonthlyIncomeCents` to 50000: `monthTotals(data, '2026-08').budgetCents` is still 100000 and `monthTotals(data, '2026-09')` too; the current month '2026-10' (no snapshot yet) shows 60000.
3. A second call returns 0 and changes nothing (deep-equal before and after).
4. No entries and `balanceStart` dated 2026-10-04: returns 0 and creates no snapshot for September or earlier. No entries and `balanceStart` dated 2026-08-04: returns 0 (empty months are not frozen).
5. An already frozen month is not overwritten (budget differs in the stored snapshot).
6. Entries only in Oct 2026 (current month): returns 0.
