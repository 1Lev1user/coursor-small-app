## Goal
Screen changes stop being instant jumps (owner decision 29, quiet part): the Add expense / Add income screen rises from the bottom like a sheet and goes back down, a tab switch is a quick fade, and the month arrows slide the content in the direction of travel. Under Reduce Motion the screens change at once, as today.

## Acceptance
- `node --test test/screenMotion.test.js` exits 0
- `npm test` exits 0
- Manual (design-review): open and close Add expense, switch all tabs, month back and forward, at 390 px, light and dark (screen recording)
- Manual (owner): on the iPhone each change takes well under half a second and never blocks a tap; with Reduce Motion on, nothing moves; in a browser without View Transitions (older Safari) everything still works with instant changes

## Notes
Source: research/3.0/design-apple.md section 4 items 4 and 6; design-impeccable.md section 4 items 7, 9. Line numbers from main at 6788db8; verify.

1. `render()` rebuilds the view with `viewElement.replaceChildren()` (:481), so CSS transitions cannot run between screens. Use a same-document View Transition when available:
   ```js
   function renderWithTransition(kind) {
       const reduce = matchMedia('(prefers-reduced-motion: reduce)').matches;
       if (reduce || !document.startViewTransition) { render(); return; }
       document.documentElement.dataset.transition = kind;   // 'tab' | 'month-next' | 'month-prev' | 'sheet-open' | 'sheet-close'
       document.startViewTransition(() => render()).finished
           .finally(() => { delete document.documentElement.dataset.transition; });
   }
   ```
   Browser support of `document.startViewTransition` in the owner's iPhone Safari is [unverified]; the fallback is today's instant render.
2. CSS, all inside `@media (prefers-reduced-motion: no-preference)`: give `.tabbar` and the app header their own `view-transition-name` so they stay still. Tab: old view fades out 120 ms, new fades in 160 ms. Month: `[data-transition='month-next']` new content enters with `translateX(12px)` plus opacity, `month-prev` with `-12px`, 200 ms `var(--ease)`. Add screen: `sheet-open` new view enters with `translateY(24px)` plus opacity over 280 ms `cubic-bezier(0.32, 0.72, 0, 1)`; `sheet-close` the old view leaves downwards over 200 ms.
3. Which calls get which kind: tab buttons `tab`; month arrows in monthNav.js `month-next` / `month-prev`; opening Add expense or Add income from Home `sheet-open`; Back or a successful save `sheet-close`. Every other render stays plain `render()`.
4. Tests `test/screenMotion.test.js`: with a fake `document` lacking `startViewTransition`, `renderWithTransition` calls `render` once (export it or the decision function for the test); with a fake `matchMedia` reporting reduce, it calls `render` directly; style.css has `view-transition-name` on the tab bar and every `::view-transition` rule sits inside `@media (prefers-reduced-motion: no-preference)`.

Amendment 2026-10-05 (planner check at 9d1590e): `src/app.js` cannot be imported under Node, so the testable helpers live in `src/motion.js` (added to allowed_paths). The kind is detected inside `render()` by comparing the last shown screen (tab, `addScreenTitle()`, monthKey) with the new one, because the Add panel opens and closes in src/views/add.js (not allowed) and C-050's test pins `goTo`.
