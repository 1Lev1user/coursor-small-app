## Goal
A genuinely new payment that happens to reuse a bank reference (a top-up reference, a camt running number "1", "2") is no longer marked "Exact: already imported" and left out by default when its date and text differ from the stored entry. Today reference + direction + amount within 5 days is enough, so the missing payment is silent unless the person opens the Duplicates step.

## Notes
Source: D-bank.md problem 11a (VERIFIED, probe p09_dups.mjs D7, D8), independently confirmed in D-bank-verify.md item 8 (probe c8.mjs: stored expense 10.00 on 2026-03-10 with bankRef REF-1; a new row `out` 10.00, same ref, another shop's text gives `exact` at +0, +2 and +5 days, `include` false by default; +6 days and a different amount are clean). The verifier rated it a wrong default rather than silent loss, because the person can tick the row in the Duplicates step. Which reference field a given bank fills (camtBankRef prefers AcctSvcrRef, then NtryRef, then EndToEndId, xml.js:457-470) is bank-specific and UNVERIFIED: verify with the owner's sample file whether the reference is unique per payment.

Cause: `byReference` (src/import/core.js:105-113) accepts a stored entry with the same `direction|bankRef` when the amount matches and `|days| <= 5`, ignoring the text.

Fix: a reference match is Exact only when at least one holds: (a) the dates are at most 1 day apart (booking versus value date); (b) the row's normalised text (`rowText(row)`, :36) equals the stored entry's text, taken from the tail of its stored `fingerprint` (format `date|amountKey|direction|text`, optionally followed by `#n`; the text may itself contain `|`, split at the third `|` only); (c) the reference is "strong": at least 12 characters and not purely digits (a bank transaction id such as `RF2026091400001`); strong references keep the 5-day window. Otherwise fall through to the existing probable, weak and ignored checks, so the row can still be reported Weak when the amount is within 2 days. The stored fingerprint of older entries may be unparseable (test fixtures use 'x' or 'fp-aug'): then rule (b) simply does not apply.

The rule was prototyped by the planner on a copy of core.js: all 30 tests of importCore.test.js pass and cases 1-5 below give the stated levels (case 1 null, 2 exact, 3 exact, 4 exact then null, 5 null then exact; the +2 days different-text row is 'weak').

Regression tests (new file, synthetic; build `data` with `defaultData()` as importCore.test.js:563 does; stored entry fields: `id`, `categoryId`, `subcategoryId: ''`, `amountCents`, `note`, `date`, `bankRef`, `importId: 'imp_a'`, `fingerprint: fingerprint(storedRow)`):
1. The failing input from the research: stored expense 1000 cents on 2026-03-10, `bankRef: 'REF-1'`, fingerprint of a row with text `SHOP A`. New row `out` 1000 on 2026-03-13 with `bankRef: 'REF-1'` and text `SHOP B`. EXPECTED: level is not 'exact' (null, because 3 days is outside the 2-day weak window). ACTUAL before: 'exact'.
2. Same stored entry, new row at +0 and at +1 day with text `SHOP B`: 'exact' (dates within 1 day, as today).
3. New row at +5 days with the SAME text `SHOP A` and the same ref: 'exact' (text rule).
4. Strong reference: stored and new ref `RF2026091400001`, different text, +5 days: 'exact'; the same at +6 days: not exact (control, as today).
5. Running-number case (research D8): stored camt-style ref `1`, 1000 cents, 2026-03-10; new row ref `1`, 1000 cents, 2026-03-14, different text: not exact. Same at 2026-03-11: exact.
6. Different amount with the same reference at +2 days: not exact (control, as today). A stored entry with fingerprint `'x'` and the new row on the same date: exact.
7. A row that fails the reference rule but lies within 2 days of a stored same-amount entry is reported 'weak' (for example ref reused, text different, +2 days).
