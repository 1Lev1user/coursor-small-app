## Goal
An imported card payment is dated on the purchase day from the card memo (`split.date`), which can be days before the bank books it. Money now is the bank account, so it must follow the booking date. Found on the owner's real statement (2026-10-18): with Money now set at the statement's opening balance on 1 Oct, five card payments bought on 28 to 30 Sep but booked in October are left out of Money now, so the app shows €50.00 more than the bank's closing balance, and "Align with the bank" would add a €50.00 Bank difference expense that is already counted in September's spending. After this card Money now and the import's bank comparison use the booking date, while spending, budgets and the Month list keep the purchase date.

## Notes
- `rowsToStatement` (src/import/text.js): when the row date comes from the card memo (`split.date` set and different from the column date), add `bookedOn: <column date>` to the statement row. No key otherwise, so existing results stay deepEqual.
- `buildImport` (src/import/core.js): copy `bookedOn` onto the expense or income entry only when present. Transfers already use the column date and need no change unless the planner finds otherwise.
- src/balance.js: `balanceAt` uses `entry.bookedOn ?? entry.date` to decide whether an entry is inside [anchor date, date]. Nothing else changes; `moneyNow`, `monthBalance`, `perDay`, `checkAgainstBank`, `alignToBank` and `startMoneyFromBank` follow through `balanceAt`. `savedCents` and per-day "spent today" keep the purchase date.
- src/model.js `normaliseEntry`: keep `bookedOn` when it is a valid YYYY-MM-DD string, delete it otherwise (same style as `editedAt`).
- Editing an entry's date in Month leaves `bookedOn` as it is (the bank booking does not move). Entries imported before this card have no `bookedOn` and keep using `date`.
- Tests (made-up data, fixed now): a card row with a memo date before the column date gets `bookedOn`; a row without a memo date has no key; the owner-shaped case (anchor on 1 Oct at the opening balance, card purchases dated 28 to 30 Sep booked 1 to 3 Oct, closing line) gives `balanceAt` equal to the closing balance and `alignToBank` difference 0; a purchase dated before the statement end but booked after it is not in `balanceAt(end)`; monthTotals still put the payment in the purchase month; normalise keeps a valid `bookedOn` and drops an invalid one.
- Amendment (planner check, 2026-10-18): `statementRow` (src/import/types.js) returns a fixed key set and would drop `bookedOn`, so types.js is added to allowed_paths: `statementRow` carries an optional `bookedOn` (added only when it is a valid YYYY-MM-DD string different from `date`) and the StatementRow typedef documents it.
- `inRange` in balance.js is shared with `savedCents`; do not change it. Add a separate helper used only by `balanceAt` (`bookedOn` when valid, else `date`).
- A stored transfer (C-115) is Money-only, so its `date` is the booking date: `row.bookedOn || row.date`. Leave `exchangeLegKeys`, fingerprints and duplicate checks on `row.date`.
- `bookedOn` must not join `EDIT_TRACKED_FIELDS`.
- Entries imported before this card have no `bookedOn`; to get the fix for an earlier statement the owner undoes that import and imports it again.
